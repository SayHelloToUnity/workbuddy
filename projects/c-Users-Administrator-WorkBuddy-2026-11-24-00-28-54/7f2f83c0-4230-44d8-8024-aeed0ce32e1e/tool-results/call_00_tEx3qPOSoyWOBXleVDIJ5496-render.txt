创作前补齐信息\n\n从零创作（含短篇）在 Read orchestrator **之前**完成；整篇美化与编辑族通常结合已有文档直接执行，只有目标、范围或保留边界确实无法从上下文确定时才补问。\n\n需要补的信息分三类：\n\n- **独占事实**：文档必须写、但模型不可能知道的输入——具体主体与对象、主推内容或核心亮点、关键数据 / 时间 / 金额等强约束。缺了正文只能编造或堆空话，必须让用户填写。\n- **风格偏好**：有多种合理走向、用户可能有明确偏好的维度——表达文风、**排版视觉风格（必问）**、受众与侧重。给 2–4 个选项并允许自定义。排版风格固定含一个「简洁排版」选项：选中后在 `user_query` 写明「简洁排版：清晰标题层级 + 正文段落，不加封面、装饰组件与配图」，下游按此收敛，不再套视觉风格。\n- **篇幅（用户未给字数时必问）**：按本次主题、体裁和用途推荐 2–3 档字数并标出推荐项，附一句各档对应的内容深度，允许自定义。例如一份酒店宣传册可给「约 800 字 · 精炼图文」「约 1500 字 · 标准版（推荐）」「约 3000 字 · 完整版」。不套用固定档位，也不默认往长写。\n用户确认的字数是硬约束：写进 `user_query` 交给下游，正文按该字数上下浮动约 10% 控制。orchestrator 据此和 prompt 中的简短表述（简短 / 简单 / 精简 / 短文 / 简报等）判断是否走短文（`brief-compose`）：出现简短表述即走短文，不判定字数；没有简短表述时再看字数，少于 2000 字才走短文。唯一定义见 `./skills/brief-compose/SKILL.md`「短文判定」，本文件不另行推断。\n\n**门禁**：用户只给一句泛泛的需求（如「写一篇年度总结」「做一个酒店宣传册」）时，不得判定为信息足够，也不得以品牌知名、文体通用为由自行脑补事实或预设风格。只有用户已给足事实、风格与篇幅，或明确表示「你来决定」时才跳过；用户全权交给模型时，按推荐档字数执行并在交付时说明所用篇幅。\n\n**不为形式而问**：标准租房合同、借条、请假条等骨架完备的通用文书直接按专业结构成稿，可变栏位留填空位；默认交付 `.docx`，不问交付格式，也不问「模板还是成稿」。\n\n**怎么问**：真实调用一次 `AskUserQuestion`，集中 3–5 个问题（通常 1–2 个事实 + 1–2 个偏好 + 1 个篇幅），不只在回复里列问题。调用后停下等待，不同时开写；拿到回答后整合进 `user_query` 再 Read orchestrator。进入 orchestrator 后链路不可中断，不再提问，未明确的非关键细节由下游按上下文处理。\n\n## 配图\n\n判别结果作为需求特征随 `user_query` 透传下游，不额外占用澄清轮次。\n\n- **需要配图**：宣传画册、文旅 / 酒店介绍、杂志刊物、新媒体软文、产品推介等依赖视觉传达的文体，或用户选了「图文并茂 / 杂志画报风」。规划封面主视觉与关键场景图，全文配图默认不超过 4 张（用户明确要求更多时从其要求）。\n- **不配图**：合同协议、起诉状、严格公文、工程规范、学术论文正文等，不加插图。\n**来源：按图位逐个判断搜图还是生图。** 判断问句：读者能否拿这张图去核对某个真实存在的特定对象？\n\n- **能核对 → 必须搜图**：具体电影剧照、真实人物、品牌与 Logo、具体地点或建筑、具体产品型号、真实事件现场等。从公开网页检索并下载（优先用必应图片、360 图片）。生成图再逼真也是编造，细节与真实对象对不上；人物、品牌还有肖像与商标风险。**不得因担心版权改用生图**，版权风险靠文末版权说明管理。检索不到合格素材就放弃该图位。\n- **不能核对 → 模型自行选择，可优先生图**：通用示意画面（一杯咖啡、现代会议室、海边日落、团队协作）、抽象概念图、封面主视觉、需全篇风格统一的插图。用 `ImageGen` 生成，免版权说明、无水印与分辨率问题。\n- **搜图合计限时 30 秒**：全文所有图位的检索加下载合计不超过 30 秒，到时立即停止搜图，不重试换源；下载命令自带超时（如 `curl --max-time`）。尚未拿到合格素材的图位：通用画面转生图；能核对的特定对象直接放弃，不生成替代图。\n- 两者都不可用时放弃该图位，不用占位图或假链接。\n**批量并发，禁止逐张往返**：图位与提示词定稿后，把全部 `ImageGen` 调用（或全部搜图、下载调用）放进**同一条消息的同一个工具调用块**一次提交，由运行时并发执行；拆成多条消息就退化为「发一张、等返回、再发下一张」，耗时约为 n 倍（实测 4 张顺序约 56 秒，并发约 17–25 秒）。提交前：\n\n1. 先加载生图工具定义（如 `ToolSearch` 载入 `ImageGen`），只做一次；\n2. 全部提示词定稿，并发后没有「看一张再改下一张」的机会——确需依据前一张调整后续提示词时才有意串行，并在交付说明里讲明；\n3. `mkdir -p` 预建输出目录，**每个图位单独一个子目录**（如 `images/slot-1/`）：生图工具不收文件名、返回顺序也可能与请求错位，分目录才能确定哪张对应哪个图位。\n同一纪律适用于其他批量操作：多张图的格式转换与压缩合并成一个脚本或一次调用，多条产物校验命令合并执行，不逐个往返。\n\n**筛选**：每个图位取若干候选，拼成一张 contact sheet（缩略图网格并标注编号）目视比对后再挑；淘汰分辨率不足、画幅重复、与正文对不上（地点、年代、型号错位）的图。合格候选不够就减少图位，不凑数。\n\n**带水印或机构标识的图可以用，但必须标明风险**：同等条件下优先挑无水印的；无水印候选不够时，带水印的图照常入选，但要 ① 在图注里点明出品方与水印来源（如\"图片来源：XX 研究院（原图带该机构水印）\"）；② 在下面的「图片来源与版权说明」里单列这些图，提示其带第三方水印、仅供内部参考，未获授权不得公开发布、印刷或商用。只有两种情况不用：水印遮挡到图的关键内容已看不清，或用户已说明用途是对外发布 / 印刷 / 商用（此时按该节末尾的规则改走生图或放弃该图位）。\n\n处理后的图片落到 Stage 2 的 `images/` 目录。Pillow 不可用时先 `python3 -m pip install --user Pillow` 一次；仍失败则跳过后处理、用原图，并在交付说明里讲明。\n\n**排版**：HTML 中 `src` 用**绝对路径**（相对路径与 `file://` 转 docx 后图片丢失）。图片**默认居中**（写法见 `agents/references/html_rules.md` §8-h）。配图要与版式融合——控制显示宽度、图文混排或网格对齐、必要时加图注，不整块大图占版面，不每段塞图。\n\n**版权说明**：只要用了网络图，正文末尾必须单列「图片来源与版权说明」：注明来自公开网络检索、按顺序列出各图来源站点或链接，**其中带第三方水印或机构标识的图要逐条标出水印出品方并提示该风险**，并声明：仅供内部参考与交流，**未获授权，禁止用于公开发布、印刷、商用及任何商业场景**，如需上述用途请替换为官方物料或正版图库授权素材。该节不能因版式好看而省略。用户已说明用途是对外发布、印刷或商用时，不用网络图：通用画面改走生图；特定真实对象请用户提供已授权素材，否则放弃该图位，不生成替代图。这是免责说明，不构成授权。\n\n## 编辑及其他\n\n不属于上述任何生成族 route 的 .docx 操作，一律归编辑族，**转交外部编辑 skill**（`workbuddy-office-routing` / `workbuddy-local-office-edit`）。转交时带上用户原始意图与 .docx 文件路径，本 skill 调用随之结束。常见形态：\n\n-
